## 🔄 去重策略对比

### **各数据类型的去重策略**

| 数据类型 | 去重规则 | 允许重复 | 原因 |
|---------|---------|---------|------|
| **门店数据** | 日期 + 门店名称 | ❌ 否 | 每个门店每天只有一条数据 |
| **订单数据** | 订单号 | ❌ 否 | 订单号是唯一标识 |
| **商品数据** | 无去重 | ✅ 是 | 同一商品可能有多条记录 |
| **评价数据** | 待定 | 待定 | 未实现 |
| **成长数据** | 待定 | 待定 | 未实现 |
| **粉丝群数据** | 待定 | 待定 | 未实现 |

## 💡 为什么商品数据允许重复？

### **业务场景示例**

#### **场景1: 同一商品多次上架**
```
日期: 2025-10-17
门店: 圣比萨(鲍岛店)
商品: 玛格丽特披萨

记录1: 上午上架，销售额 100 元
记录2: 下午上架，销售额 50 元
```

如果去重，会丢失其中一条记录，导致销售数据不完整。

#### **场景2: 不同批次的数据**
```
同一天，同一门店，同一商品
可能来自不同的导出时间点
每个时间点的销售数据不同
```

## 🔍 如何处理重复数据？

### **方案1: 保留所有数据（当前方案）**
- ✅ 优点：不丢失任何业务数据
- ✅ 适用：需要完整的历史记录
- ⚠️ 注意：需要在查询时聚合数据

### **方案2: 数据聚合（可选）**
在查询层面进行聚合：
```sql
SELECT 
    data_date,
    store_name,
    product_name,
    SUM(sales_amount) as total_sales,
    SUM(sales_volume) as total_volume
FROM eleme_product_data
GROUP BY data_date, store_name, product_name
```

## ⚠️ 注意事项

### **1. 数据库设计**
- 商品表没有唯一约束（unique constraint）
- 只有普通索引（index）
- 允许插入完全相同的记录

### **2. 查询性能**
- 重复数据会增加表的大小
- 查询时可能需要 GROUP BY 聚合
- 建议定期清理历史数据

### **3. 数据分析**
- 在做销售分析时，注意是否需要去重
- 使用 SUM() 聚合函数时要小心
- 可以通过 import_batch_id 区分不同批次
